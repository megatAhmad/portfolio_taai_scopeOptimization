Problem Flow Algorithms

1. Problem And Solution Overview

From spreadsheet guesswork to an auditable shutdown scope engine.

Shutdown planners often reconcile several equipment datasets manually with VLOOKUP-heavy workflows. That creates inconsistent joins, hidden omissions, untraceable business logic, and no single place to explain why one equipment item was marked as compulsory while another was excluded. This platform replaces that with guided dataset intake, confidence-aware matching, derived evidence generation, a visual rules engine, and fully exportable classification output.

3 Decision outputs: Must Have, Good to Have, Not Needed
2 Main input roles: canonical source-of-truth data and supplementary evidence datasets
100% Auditable run model with rule trace, source fields, persisted artifacts, and CSV export

Core Problem

What the platform fixes

The goal is not only to classify equipment, but to make every inclusion and exclusion explainable to planners and engineers.

Messy Equipment IDs

The same equipment may appear as P100, P-100, or a partially normalized tag across different files.

Buried Logic

Spreadsheet formulas hide the reasoning and are difficult to version, inspect, or reset.

No Audit Trail

Stakeholders struggle to answer: which source matched, what rule fired, and what evidence justified the outcome?

Solution summary
  • Guide users through upload, inspection, and schema mapping.
  • Build a master dataframe that preserves canonical rows and aggregates supplementary evidence.
  • Allow typed derived columns to convert raw source signals into rule-friendly helper fields.
  • Let users create versioned AST-based rules for classification.
  • Persist classification runs as artifact-backed outputs for scale, explainability, and export.

2. Process Flow

How the solution moves from raw files to final scope

Each stage narrows uncertainty: first schema certainty, then matching certainty, then rule certainty.

01

Project Creation

A project isolates all datasets, rulesets, and classification runs so teams can work on one shutdown scope at a time.

02

Dataset Inspection

CSV files are profiled immediately. Excel files first expose workbook sheet names, then only reveal preview/schema after explicit sheet selection.

03

Schema Mapping

Users map source columns into canonical-friendly names. Validation blocks missing targets, duplicate targets, and excluded join or equipment ID fields.

04

Derived Evidence Generation

Typed conditions convert raw dataset values into helper labels such as due-status, outage windows, or domain-specific text flags.

05

Master Dataframe Construction

The canonical dataset remains the left-hand anchor. Supplementary datasets are matched and aggregated so duplicate evidence is preserved rather than overwritten.

06

AST Rule Evaluation

Rules are executed in order: Must Have first, then Good to Have, then fallback classification.

07

Persisted Run Artifacts

Rows, explanations, and export files are stored as artifacts. The database keeps metadata and artifact references so large runs stay queryable.

Component Map

What each part of the solution owns

The platform is split into clear responsibility zones so ingestion, reasoning, and persistence can evolve independently.

Frontend

Guided Intake UI

Project workspace, upload form, Excel intercept modal, mapping grid, derived columns editor.

  • Prevents invalid uploads before they hit the backend.
  • Shows schema previews and mapping suggestions.
  • Keeps the user inside an auditable workflow.
Backend

Dataframe Engine

Profiles files, applies mappings, computes derived fields, joins evidence, and runs typed conditions.

  • Reads CSV and Excel datasets.
  • Normalizes and matches supplementary sources.
  • Produces the master dataframe used for classification.
Backend

Rules And Run Persistence

Stores versioned AST rulesets, classifies rows, and persists run artifacts for export and review.

  • Returns row-level explanation traces.
  • Supports paginated result loading.
  • Uses Alembic migrations for schema control.

3. Algorithms And Methods

What logic exists inside each component

This section documents the exact kinds of methods the platform exposes today.

Exact Matching

Compares the canonical join value against the supplementary equipment identifier without normalization. Best for clean, standardized IDs.

Method: exact Confidence: 1.0 Use when IDs are governed

Normalized Matching

Lowercases text, strips whitespace, and removes non-alphanumeric characters so values like P-100 and p100 resolve together.

Method: normalized_exact Confidence: 1.0 Tolerates punctuation drift

Fuzzy Matching

Uses a similarity score to compare normalized values and accepts the best candidate only when it meets the configured threshold.

Method: fuzzy Threshold: configurable Good for messy source IDs

Duplicate Evidence Aggregation

If multiple supplementary rows match one canonical row, the platform keeps all of them as aggregated evidence instead of overwriting earlier rows.

  • *__matched_source_ids
  • *__match_count
  • *__match_confidences
  • *__evidence_rows
How matching confidence is exposed

The master dataframe retains summary fields such as match method, per-run confidence, and full evidence rows so reviewers can see whether a classification relied on clean joins or softer fuzzy matches.

Text-Derived Conditions

Used when the source field is textual or tag-based.

= != CONTAINS CONTAINS ANY CONTAINS ALL IN

Numeric-Derived Conditions

Used for thresholds such as maintenance age, count, duration, pressure, or cost bands.

< > <= >= BETWEEN

Date-Derived Conditions

Supports planning logic such as due windows, outage eligibility windows, or date-based triggers.

< > <= >= BETWEEN

Fallback Outputs

Each derived field can emit typed outputs for successful matches, failed matches, or null/empty source cells.

  • true_value
  • false_value
  • null_value
How derived rules behave on aggregated list values

When a matched supplementary field contains multiple values, the engine evaluates the condition across the list. For text searches, combined content can be searched; for scalar comparisons, the rule passes if any value satisfies the condition.

Rule Model

Classification rules are stored as AST trees made from nested groups and typed condition nodes.

  • Group nodes use AND or OR.
  • Condition nodes target one field, one operator, and one expected value set.
  • Node ids stay stable for explanation traces.

Execution Order

The engine evaluates the rules in a fixed priority order so classifications stay deterministic.

1. Must Have 2. Good to Have 3. Fallback Label

Trace Output

Every row can return the evidence path behind the decision.

  • matched_rule
  • rule_path
  • source_fields
  • condition_trace

Persisted Result Model

Large run outputs are stored as artifacts rather than one oversized JSON database row.

  • Rows artifact: JSONL
  • Explanation artifact: JSONL
  • Export artifact: CSV
  • Metadata stays in the database
Why AST-based classification matters

AST rules make the engine versionable, inspectable, and explainable. Instead of opaque spreadsheet formulas, each logical group and condition becomes a stored structure that the UI can render, save, compare, and trace back during classification review.

Decision Story

What a reviewer can now explain

The solution is designed so an engineer or planner can defend a row without leaving the product.

Why it matched

The reviewer can inspect the matching method and evidence rows tied to that canonical equipment item.

Why it classified

The reviewer can inspect the AST path, condition outcomes, and source fields involved in the final decision.

Why it scales

The reviewer still gets exportable and pageable output even when classification results grow beyond what one JSON row should hold.
